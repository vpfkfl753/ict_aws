# Tacit 개발 SSOT

합의일: 2026-09-21. 개발 기준은 이 저장소와 Git으로 관리한다.
이 문서는 사용자와 합의한 목표 설계다. 구현 완료나 실제 실행 성공을 뜻하지 않는다.
기존 마일스톤·실험 기록은 해당 시점의 증거로 보존한다.

## 사용 화면

- 일상 사용, 설정, 승인, 기록 조회를 Slack 안에서 제공한다. 이번 버전에는 별도 관리자 웹을 만들지 않는다.
- 사람 간 DM은 원문 대화와 `/tacit-send`의 진입점이다.
- Tacit 봇 DM은 맥락 공유 승인·수정·취소, 확인 질문, 최종 설명을 담당한다.
- 작업별 봇 스레드에서 공유된 Agent 간 질문·답변과 진행 상황을 확인한다.
- App Home에서 허용 자료 폴더, 웹 검색 여부, 실행기·모델, 연결 상태, 최근 작업을 관리한다.
- 로컬 워커 설치와 외부 실행기 계정 로그인은 해당 머신/인증 브라우저에서 진행한다.

## 자료 수집과 개발 범위

- 목표는 메시지 의도 파악 → 필요한 정보 판단 → 허용 범위 검색 → 부족하면 추가 탐색 → 근거 포함 맥락 생성이다.
- 사용자가 지정한 디렉토리의 하위 파일을 자율 검색·읽을 수 있다. 공개 웹 검색·열람도 설정으로 허용한다.
- 자료 조회 권한에 파일 수정·임의 명령 실행 권한이 포함되지는 않는다.
- 디렉토리 밖으로 이어지는 심볼릭 링크 및 인증 파일은 수집 대상에서 제외한다.
- 비공개 원문을 공개 웹 검색어로 자동 전송하지 않는다.
- **현재 개발·실험 자료는 `/home/user/work/ict_aws/examples/`와 `demo/`의 합성 데이터만 사용한다.**
- **`~/lab_project`와 실제 연구자료는 접근하지 않는다.** 앞선 설계 설명의 경로 예시는 접근 허가가 아니다.
- 이번 단계에서 추가 컨테이너·OS 수준 격리를 도입하지 않는다. 설정 범위와 자료 수집 코드로 제한한다.

## 원문과 추가 맥락 전송

- 원문 DM은 추가 맥락 승인과 독립적으로 먼저 보낸다. 맥락 생성 때문에 원문을 지연하지 않는다.
- 현재 구현은 송신 워커가 원문을 전송하므로 워커가 꺼지면 원문도 대기한다. 항상 즉시 전송되는 것은 아니다.
- 원문 전송 뒤 맥락 처리 상태를 Slack에서 보여준다.
- 추가 맥락은 최초에 반드시 송신 사용자에게 보여주고 승인받는다.
- 승인 UI는 포함할 내용·근거를 확인하고 수정·제외·승인·취소할 수 있어야 한다.
- 승인 전에 상대 Agent 또는 중앙 서버에 로컬 초안·검색 원문을 업로드하지 않는다.
- Slack 승인 화면에 표시하는 요약은 Slack으로 전송되는 정보다. 전체 검색 기록·원본 자료는 자동 첨부하지 않는다.
- 사용자가 수정한 최종 승인 버전을 상대에게 전달한다. 승인과 전송에는 사용자·상대·작업·버전 정보를 연결한다.

## Agent 간 추가 대화

- 최초 맥락을 받은 상대 Agent가 부족한 정보를 질문할 수 있다.
- 최초 전달 뒤 추가 질의는 최대 2왕복으로 시작한다.
- 이미 승인해 공유한 맥락 안에서 답할 수 있으면 자동으로 답변한다.
- 새 로컬 정보를 공유해야 하면 해당 정보를 가진 사용자에게 다시 승인받는다.
- 검색과 추가 질의로 해결되지 않으면 자기 사용자에게 Slack으로 짧게 질문한다.
- 사용자 답변 대기 중에는 관련 작업만 대기하며, 추정을 사실로 확정하지 않는다.
- 외부 문서·수신 맥락·Agent 답변은 자료로 취급하며 권한 확대나 실행 지시로 취급하지 않는다.

## 기록과 열람 범위

| 데이터 | 보관 위치 및 열람 |
|---|---|
| 검색 원문·원본 자료·공유 전 전체 초안 | 해당 사용자 머신 |
| 승인한 맥락·교환한 Agent 대화·처리 상태 | 중앙 DB에 저장 |
| 사용자의 작업 조회 | 자기 기록과 자신이 참여한 교환만 제공 |
| 중앙 관리자 기본 화면 | 연결 상태·오류 등 운영 정보 중심 |

- 관리자가 기본 화면에서 보지 않는다는 것과 서버 운영자가 기술적으로 접근할 수 없다는 것은 다르다. 현재 중앙 저장은 종단간 암호화가 아니다.
- Slack은 기록을 표시하는 화면이며 중앙/로컬 저장소가 기록 원본이다.
- 양쪽이 승인한 교환 내용을 작업 순서대로 보여준다. 상대의 미공유 원본이나 승인 전 초안을 노출하지 않는다.
- 감사 대상은 접근 자료, 실행한 도구, 공유 승인·전송, Agent 메시지, 상태 전이다. 모델 내부 사고 과정의 수집·공개는 요구하지 않는다.

## 실행기와 검증

- `codex`, `kiro`, `opencode` 선택 구조를 유지한다. 각 사용자는 자기 계정·구독을 사용한다.
- 실행기를 바꿔도 Slack·중계·맥락 교환 계약은 유지한다.
- Kiro는 adapter 존재와 실제 로그인·모델 응답 성공을 구분해 검증한다.
- 제품 실험은 실제 Tacit 워커·중계·Slack 명령을 통과해야 한다. 별도 모의 흐름을 제품 실험 성공으로 대체하지 않는다.
- 변경에 필요한 단위 테스트는 사용할 수 있지만 실제 모델 응답·수신 확인·설명 품질의 증거와 구분한다.
- 상대 사용자 반응만으로 제품 유용성이나 실패를 판정하지 않는다. 양쪽 자료와 실험 전제, 실제 생성된 설명을 확인한다.

## 현재 구현과 남은 작업

| 기능 | 2026-09-21 확인 상태 |
|---|---|
| 수동 Slack 명령·중계·두 사용자 워커 | 구현됨, 과거 실제 연결 증거 있음 |
| Codex 로컬 자료 기반 생성 | 실제 호출 증거 있음 |
| Kiro/OpenCode adapter | 구현됨. Kiro는 실제 Tacit 송신 응답 생성 확인; 수신 및 OpenCode 모델 호출은 별도 확인 필요 |
| 의도 기반 자율 자료 검색·웹 검색 | 미구현; 현재는 지정 폴더의 제한된 텍스트 발췌 |
| 공유 전 승인·수정 | 미구현 |
| Agent 간 최대 2왕복·사용자 확인 질문 | 미구현 |
| Slack Home 설정·작업 감사 화면 | 미구현 |
| 승인 전 정보의 중앙 비전송 | 새 승인 구조에서 구현·검증 필요 |

권장 구현 순서: Kiro 실제 연결 → 허용 자료 자율 검색 → Slack 공유 승인 → Agent 간 추가 질의 → Home 설정·기록 조회.
인증에 필요한 사용자 조작이나 상대 머신의 준비가 막혀도 독립적인 구현 작업은 계속할 수 있다.
실제 사용자 데이터 접근이나 제품 범위 변경은 기존 합의로 간주하지 않는다.
