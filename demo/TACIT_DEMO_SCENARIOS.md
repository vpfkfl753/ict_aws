# Tacit 발표·데모 시나리오 3종

작성일: 2026-09-17

## 데모가 보여줄 핵심

사람이 Slack에서 보내는 문장은 짧고 자연스럽다. 문제는 양쪽 사용자가 서로 다른 문서,
실험 조건, 구현 범위를 보고 있어도 그 차이가 문장에 드러나지 않는다는 점이다.

Tacit은 기존 사람 간 DM을 그대로 보내면서, 별도의 Agent Plane에서 양쪽 로컬 자료를 비교해
다음 내용을 수신자에게만 설명한다.

1. 상대가 어떤 전제를 기준으로 말했는지
2. 내 자료와 무엇이 다른지
3. 지금 확정할 수 있는 사실과 아직 확인할 것이 무엇인지

## 시나리오 1. VLM 실험 기준선 불일치

### 상황

재용은 8월 실험 B17을 공식 기준선으로 알고 있다. B17은 preprocessing p2와 dataset split
v3를 사용하며, 성공 조건은 동일 입력 조건에서 B17 대비 정확도 2%p 향상이다.

성원의 현재 노트북은 B24를 기준으로 한다. B24는 preprocessing p3와 dataset split v3를
사용한다. 새 모델은 B24 대비 2%p 향상됐지만 B17/p2 조건으로는 아직 재실행하지 않았다.

### 일반 Slack 문장

```text
현재 비교는 B24 기준인데 B17 조건으로 다시 맞춰볼까요?
```

문장만 받은 사람은 B17과 B24가 무엇인지, 왜 다시 맞춰야 하는지 알기 어렵다.

### Tacit이 설명해야 하는 내용

- B17/p2와 B24/p3는 비교 기준과 전처리가 다르다.
- 현재 +2%p는 B24 대비 결과다.
- B17 대비 성공이라고 발표하려면 B17/p2 조건으로 재실행해야 한다.
- 재실행 전에는 발표 문구를 `B24 대비 +2%p`로 제한해야 한다.

### 실제 실행 결과

2026-09-17 SERA LAB에서 실제 `/tacit-send`를 사용했다.

- 전달 ID: `56b36628-78ac-4a41-ae17-ef5b44fa3259`
- 우성원 명의의 원문 DM 전달: 확인
- 우성원 worker의 sender context 생성: `prepare completed` 확인
- Agent 설명 전 재용의 반응: `B24 B17이 대체뭐예요`

이 반응은 User Plane의 짧은 문장만으로 전제가 전달되지 않는다는 문제를 실제로 보여준다.
재용의 Tacit 봇 DM에 비교 조건 설명이 도착했는지와 설명 품질은 재용 화면에서 확인해야 한다.

발표 화면 구성은 `일반 DM의 혼란 → 개인 Tacit 설명 → 비교 조건 정정` 순서가 좋다.

## 시나리오 2. API 계약 버전 불일치

### 상황

송신자는 배포 후보인 API v2.1 문서를 보고 있다.

- endpoint: `POST /v2/context/send`
- 수신자 필드: `recipient_agent_id`
- 필수 필드: `evidence_version`, `consent_scope`

수신자 구현은 기존 v1 계약을 사용한다.

- endpoint: `POST /v1/exchanges`
- 수신자 필드: `recipient`
- v2 필수 필드를 보내지 않음
- 스테이징 테스트도 v1로만 통과함

### 일반 Slack 문장

```text
이 명세대로 붙이면 오늘 배포해도 되죠?
```

양쪽이 서로 다른 문서를 보고 있기 때문에 `이 명세`가 같은 대상을 뜻하지 않는다.

### Tacit이 설명해야 하는 내용

- 송신자는 v2.1, 수신자는 v1 계약을 기준으로 말하고 있다.
- endpoint, 수신자 필드, 필수 필드가 모두 다르다.
- 현재 구현을 그대로 배포하면 요청이 실패할 가능성이 높다.
- v2 migration과 스테이징 재검증 전에는 배포 합의로 해석하면 안 된다.

### 발표 포인트

단순 문서 검색은 각 문서를 따로 보여줄 뿐이다. Tacit의 가치는 현재 대화의 `이 명세`가
양쪽에서 서로 다른 버전을 가리킨다는 사실을 찾아주는 데 있다.

## 시나리오 3. 이번 발표 범위와 장기 계획 혼동

### 상황

개발 백로그에는 다음 기능이 후속 후보로 있다.

- 일반 DM 자동 감지
- `@broadcast`
- 지속적인 암묵지 갱신

하지만 발표 범위 문서에는 수동 `/tacit-send`와 개인화 설명 수신까지만 확정돼 있다.
자동 기능은 추가 Slack 권한과 개인정보 검토가 필요하며 이번 발표에서는 향후 계획으로만
소개하기로 했다.

### 일반 Slack 문장

```text
자동 모드까지 이번 발표에 넣는 걸로 된 거죠?
```

### Tacit이 설명해야 하는 내용

- 백로그에 존재하는 것과 이번 발표에 승인된 것은 다르다.
- 확정 범위는 수동 명령 기반 흐름까지다.
- 자동 감지와 broadcast는 개인정보 검토가 필요한 향후 계획이다.
- 발표에서 구현 완료로 표현하거나 실제 시연하면 안 된다.

### 발표 포인트

이 시나리오는 버전 차이뿐 아니라 `계획`, `승인`, `완료` 상태가 섞일 때 생기는 오해를
보여준다. Agent는 사용자의 의도를 대신 확정하지 않고, 근거가 있는 범위와 미확정 범위를
구분해야 한다.

## 실제 시연 순서

1. 양쪽 worker가 해당 시나리오의 서로 다른 자료 폴더를 읽도록 설정한다.
2. `/tacit-status`에서 두 사용자 모두 `최근 연결됨`인지 확인한다.
3. 송신자가 시나리오의 짧은 `/tacit-send` 메시지를 보낸다.
4. 사람 간 DM에는 원문이 그대로 도착하는 것을 보여준다.
5. 수신자의 Tacit 봇 DM에서 전제 차이·근거·미확정 사항을 확인한다.
6. 양쪽 사용자가 설명이 실제 업무 맥락과 맞는지 확인한다.

시나리오별 원본 데이터는 같은 폴더의 `01_experiment_baseline`, `02_api_contract`,
`03_demo_scope` 아래에 있다.

## Kiro 연결 범위

현재 구조에서 Kiro를 붙일 때 바뀌는 핵심은 Agent 프로세스 내부의 runtime/provider다.
Slack 명령, User Plane DM, 중계 서버, Agent Plane 교환 프로토콜은 유지한다.

추가로 달라지는 것은 사용자별 Kiro 로그인, 모델 선택, tool 권한, Kiro 응답 이벤트를 공통
출력 형식으로 바꾸는 adapter다. 따라서 발표 플로우차트에서는 보라색 Agent 프로세스 내부의
추론 실행기만 Codex/OpenCode/Kiro 중 선택되는 형태로 그리면 된다.
